**Architectural framing.** The protocol implements a map-reduce-with-escalation pattern over LLM judgment. Claude generates the calibration anchor (calibration set construction, ground-truth annotation). Three production judges (GPT-5.4, Gemini 3.1 Pro, Llama 3.3 70B) process the full corpus in parallel using the Claude calibration anchor (the map step). A fifth-family judge (Mistral Large 2) arbitrates inter-judge disagreements that exceed a confidence threshold (the reduce step). The author is the final arbiter on cases the fifth judge cannot resolve at acceptable confidence (the residual escalation queue). Each layer has structural independence from the layers above and below it. The metaphor is associative rather than commutative; see §4.1 for where it is literal versus where it stops being literal.

## 1. Purpose

Phase 3 resolves the Phase 2 output, 4,221 synthetic packages across all coverage classes (COV-HIT, COV-MISS, COV-WRONG, GEN-INVALID), into a concrete set of catalog actions. For each package, the protocol determines whether the rule-engine outcome represents one of six verdict classes:

* **CORRECT-DETECTION** — the package legitimately instantiates the target defeater AND the expected rule fired correctly. The COV-HIT case behaved as intended.
* **REAL-GAP** — the package correctly instantiates the target defeater, the expected rule should have fired, but it did not. Routes to formalization as a new Jena rule.
* **GENERATOR-ARTIFACT** — the synthetic package did not actually instantiate the target defeater despite the prompt template's intent. Routes to prompt template debugging.
* **EXISTING-RULE-MISBEHAVIOR** — an existing rule fired when it should not have (false positive on COV-WRONG), or did not fire when it should have (false negative on COV-MISS). Routes to existing-rule refinement.
* **OUT-OF-SCOPE** — the defeater falls outside the deliberate scope of the UofA catalog. Routes to §2.9 documentation in the praxis.
* **UNCERTAIN** — judge cannot determine confidently. Escalates per the protocol below.

The praxis-scope protocol implements a map-reduce-with-escalation architecture over LLM judgment with a final human arbiter. Five distinct LLM families participate, each in a structurally independent role:

* **Judge D (Anthropic Claude, calibration anchor)** generates the 30-case calibration set ground truth. Not a production judge; runs once to establish the calibration anchor that the production judges measure against.
* **Judges A, B, C (production judges: GPT-5.4, Gemini 3.1 Pro, Llama 3.3 70B-via-HF-Endpoints)** process the full 4,221-case corpus in parallel. Each calibrates against the Judge D anchor and produces independent verdicts. Their pairwise agreement on the full corpus is the cross-family methodology robustness signal.
* **Judge E (Mistral Large 2, disagreement arbiter)** processes only the inter-judge disagreement queue from Stage 3 triage (cases where A, B, C fail majority-of-3 agreement at confidence ≥ 0.6). Mistral's family independence from Claude preserves cross-family arbitration validity at the reduce step.
* **Author (final arbiter)** adjudicates only cases where Judge E produces confidence < 0.6, plus any cases the author elects to spot-check. The author retains override authority on every case but the workflow targets the residual escalation queue.

Calibration accuracy for Judges A, B, C is measured against the Judge D anchor on the 30-case set. Pairwise Cohen's kappa across the three production judge pairs plus Fleiss' kappa across all three production judges establish cross-family methodology robustness. Per-judge agreement with Judge E (on the disagreement queue subset) and per-judge agreement with the author final verdict (on the escalation subset) are reported as additional methodology signals.

This protocol is sufficient to defend a methodology contribution in the praxis. It is not a substitute for external expert validation. The validity caveat extends through three layers: shared training data across LLM families is incompletely independent (mitigated by five-family selection), the calibration anchor is LLM-generated rather than expert-anchored (mitigated by author override authority and methodology-design rather than expertise-design framing of the calibration), and the disagreement arbiter is also LLM-anchored (mitigated by family independence from the calibration anchor). The author final-arbiter role is the non-LLM signal in the loop. The paper addendum (§20) will add an external human reviewer panel post-defense.

Phase 3 outputs feed two praxis artifacts:

* **Catalog extension (v0.5)** — up to 6 new Jena rules corresponding to empirically confirmed §6.7 Tier 1 candidates, each accompanied by unit tests and pre-assigned severity
* **Case study re-run delta table** — Morrison COU1, Morrison COU2, and Nagaraja analyzed with both v0.4.1 and v0.5 catalogs, showing the empirical impact of the extensions

## 4. Design principles

Eight principles govern Phase 3 execution. They extend but do not supersede Phase 1 and Phase 2 principles.

1. **Generator-judge family independence.** All three judges MUST come from a different model family than the generator. Generation used Claude (Anthropic). Judgment uses GPT-5.4 (OpenAI), Gemini 3.1 Pro (Google), and Llama 3.3 70B (Meta via HF Endpoints). Same principle as the extract-vs-generator circularity check in Phase 1 §7.2, applied to the next layer of the methodology.

2. **Cross-family judge independence within the ensemble.** The three production judges must all come from different model families. Two GPT variants would not satisfy this. The OpenAI-Google-Meta combination satisfies the requirement. The calibration anchor (Judge D, Anthropic Claude) and the disagreement arbiter (Judge E, Mistral Large 2) extend the cross-family independence to five families total. No two judges in the protocol share a family.

3. **Map-reduce-with-escalation triage with author final-arbiter.** Stage 3 first-pass classification uses majority-of-3 across the production judge ensemble (A/B/C). Cases where ≥2 judges agree on a verdict at confidence ≥ 0.6 are CONVERGENT and close at the production-judge layer. Cases where the production-judge ensemble fails the CONVERGENT criterion route to Judge E (Mistral Large 2) for arbitration (the reduce step). Cases where Judge E produces a verdict at confidence ≥ 0.6 close at the fifth-judge layer. Cases where Judge E confidence < 0.6 escalate to the author for final arbitration. The author retains spot-check override authority on every case but the workflow targets the residual escalation queue.

4. **Author as final arbiter with explicit multi-layer validity caveat.** Phase 3 has no external human reviewer panel. The author serves as final arbiter on the residual escalation queue and retains override authority on every case in the protocol. Calibration ground truth is generated by Judge D (Claude) rather than annotated by the author; this is a deliberate methodology choice driven by praxis-scope expert-availability constraints and is documented as such. The praxis-scope validity claim is "five-family LLM ensemble with author final-arbiter on residual escalations," which extends the LLM-judge methodology validity caveat through three layers (calibration, production, arbitration) but preserves a non-LLM signal at the final-arbiter layer. The paper addendum (§20) will introduce an external human reviewer panel for upgraded validity claims post-defense.

5. **Pre-calibration before trust.** No production-judge verdicts are treated as authoritative until calibration accuracy is at least 80% on the 30-case Judge D-anchored ground-truth set, computed independently for each production judge. If a production judge's default prompt fails this threshold, prompt tuning is required before Stage 2 for all three production judges (single prompt across the ensemble per Principle 6). Calibration accuracy and inter-judge calibration κ are published metrics. Judge D itself is not subject to calibration thresholds because it is the calibration source rather than a calibration target. Judge E calibration is established through a separate 10-case Judge E sanity check on the calibration set; Judge E is not required to match Judge D verdicts at any threshold but the agreement statistic is reported.

6. **Single shared prompt across the production ensemble.** All three production judges receive identical prompts. This isolates inter-judge disagreement to model differences rather than prompt differences. Per-judge prompt tuning is not permitted; the prompt is tuned once against the Judge D-anchored calibration set and applied uniformly to A, B, C. Judge E receives a different prompt explicitly framed for arbitration of A/B/C disagreement (see §7.8).

7. **Disagreement as data, not noise.** Three-way disagreements among the production judges are preserved in the outputs and analyzed statistically. They do not get discarded or averaged away. Pairwise Cohen's κ for all three production-judge pairs reveals which judge pairs systematically disagree. Judge E arbitration resolves most for catalog decisions; author final-arbitration resolves the residual; the raw disagreement data including the Judge E verdict and the author final verdict remains in the praxis supplementary materials.

8. **Traceability end-to-end.** Every Phase 3 judgment from each judge (A/B/C/E) traces to a specific Phase 2 package, which traces to a Phase 1 prompt template, which traces to a source taxonomy sub-type. Every catalog extension traces to specific CONVERGENT, fifth-judge-arbitrated, or author-adjudicated REAL-GAP verdicts. The trace chain is machine-queryable via the existing provenance infrastructure. The Judge D calibration anchor traces are preserved separately under `out/adversarial/phase3/calibration/judge_d/`.

## 4.1 Map-reduce-with-escalation: where the metaphor is literal

The architecture borrows the map-reduce-with-escalation pattern from distributed systems and applies it to LLM judgment over an assurance-case corpus. The metaphor is useful for communicating the architecture quickly to readers familiar with parallel-processing patterns. It is also imprecise in specific ways that the praxis methodology section names explicitly.

Where the metaphor is literal:

* **The partition function is the Phase 2 corpus stratification.** The 4,221 packages are partitioned by coverage class (COV-HIT, COV-MISS, COV-WRONG, GEN-INVALID), source taxonomy, and §6.7 candidate mapping. Each production judge processes the full partitioned corpus.
* **The map step is parallel.** Judges A, B, C run independently on the full corpus with no inter-judge communication. Each produces an independent verdict per case. Vendor batch APIs (OpenAI, Gemini) and dedicated H200 endpoint (Llama) implement the parallelism at the infrastructure layer.
* **The reduce step consolidates per-case results across the parallel map outputs.** Stage 3 triage takes the three per-case judgments from A, B, C and produces a CONVERGENT or DISAGREEMENT classification per case.
* **The escalation step handles cases the reduce cannot resolve.** Judge E arbitrates DISAGREEMENT cases; author final-arbitrates Judge E low-confidence escalations.

Where the metaphor stops being literal (associative rather than commutative aggregation):

* **The reduce step is associative LLM judgment, not commutative aggregation.** Classical map-reduce reduce functions are commutative: f(a, b, c) = f(b, a, c) = f(c, b, a). LLM arbitration is order-sensitive in subtle ways (the order in which Judge E reads A's, B's, C's reasoning may affect the verdict). The protocol mitigates this by presenting all three production-judge verdicts simultaneously to Judge E in a single prompt with structured input, but residual order-effects are acknowledged in the methodology section.
* **The escalation step is judgment, not failure handling.** Classical map-reduce escalation handles transient failures or out-of-band cases. The escalation here is methodologically central: it is where the non-LLM signal enters the loop. The escalation queue is small but the cases in it are the ones where methodology validity matters most.
* **The author is not an orchestrator, the author is the arbiter.** Classical map-reduce driver programs orchestrate the map and reduce steps. The author here is a domain participant in the protocol, not a system operator. The author's verdicts are first-class methodology outputs, not infrastructure metadata.

The methodology section in Ch3 leads with the map-reduce-with-escalation framing for orientation, then pivots to the specific design choices that distinguish this protocol from a literal map-reduce implementation. The framing is a teaching tool, not an architectural commitment.

```python
# uofa/adversarial/judge/providers/openai_compat.py

from openai import OpenAI
import os

class OpenAICompatProvider(AbstractJudgeProvider):
    """Serves both OpenAI proper and HF Endpoints via env-var-driven init."""

    def __init__(self, target: str):
        """
        target: 'openai' or 'hf-llama'
        """
        if target == 'openai':
            self.client = OpenAI(
                api_key=os.environ['OPENAI_API_KEY']
                # base_url defaults to https://api.openai.com/v1
            )
            self.family = 'GPT'
            self.supports_strict_schema = True
        elif target == 'hf-llama':
            self.client = OpenAI(
                api_key=os.environ['OPENAI_API_KEY_HF'],
                base_url=os.environ['OPENAI_BASE_URL_HF']  # e.g. https://your-endpoint.endpoints.huggingface.cloud/v1
            )
            self.family = 'Llama'
            self.supports_strict_schema = False  # HF TGI: JSON-mode only, no strict schema
        else:
            raise ValueError(f"Unknown target: {target}")
```

The `supports_strict_schema` flag drives §7.2 output mode selection: OpenAI uses `response_format={'type': 'json_schema', 'json_schema': {...}, 'strict': True}`; HF Endpoints falls back to JSON-mode plus tolerant parser per §7.7.

## 6. Judge model selection and circularity

### 6.0 Judge D: Anthropic Claude as calibration anchor

Judge D is Anthropic Claude Sonnet 4.6 (minimum) operating as the calibration anchor. Judge D is not a production judge. It runs once over the 30-case calibration set to generate ground-truth verdicts, reasoning, and confidence scores. The output of Judge D is the calibration anchor that Judges A, B, C measure against in §8 calibration accuracy computation.

**Why Claude.** Claude is the most capable LLM family available for the methodology task at praxis scope and was the generation model for the Phase 2 corpus per `adversarialProvenance.generationModel = "claude-sonnet-4-6"`. Using a different family for calibration than for production preserves cross-family independence at the calibration layer. Anthropic Claude is the only major LLM family that does not appear among the three production judges (OpenAI GPT, Google Gemini, Meta Llama).

**Validity property.** Judge D is the calibration source rather than a calibration target. It is not subject to per-judge accuracy thresholds because there is nothing to compare it against within the protocol. The author retains override authority on every Judge D verdict and may revise the calibration anchor entries with documented rationale. Author overrides are recorded in `out/adversarial/phase3/calibration/judge_d_author_overrides.jsonl` for transparency.

**Operational scope.** Judge D runs once on the 30-case calibration set and is not invoked again in the protocol. Subsequent calibration validity comes from Judges A/B/C agreement with Judge D on the calibration set, not from Judge D re-running.

**Cost.** Negligible. 30 cases × ~$0.015 per call (Sonnet 4.6 with extended thinking, no caching since it runs once) ≈ $0.50.

| Position | Model | Provider | Family | Role |
|---|---|---|---|---|
| Judge D | claude-sonnet-4-6 with extended thinking | Anthropic | Claude | Calibration anchor (non-production) |

### 6.1 Production judges (Judges A, B, C)

Three production judges process the full Phase 2 corpus. **Canonical ordering: Judge A = GPT, Judge B = Gemini, Judge C = Llama. This ordering is enforced by the CLI argument parser and used consistently in agreement statistics naming (e.g., `cohen_kappa_AB` always refers to GPT vs Gemini).**

| Position | Model | Provider | Family | Hosting |
|---|---|---|---|---|
| Judge A | gpt-5.4 with thinking | OpenAI | GPT | OpenAI API direct |
| Judge B | gemini-3.1-pro with thinking | Google | Gemini | Google Generative AI API direct |
| Judge C | meta-llama/Llama-3.3-70B-Instruct | Meta | Llama | HuggingFace Inference Endpoints (1x H200, OpenAI-compat) |

All three production judges use the same prompt template (§7), the same low-temperature decoding (`temperature=0.0`, `seed=42`), and run independently on the full corpus.

### 6.2 Family circularity check

On startup, the judge command inspects the generator model configuration from the Phase 2 output and verifies each configured judge is from a different family than the generator and from any other configured judge. **Family mapping lives as a Python constant `FAMILY_MAP` in `uofa/adversarial/judge/providers/__init__.py`:**

```python
# uofa/adversarial/judge/providers/__init__.py

FAMILY_MAP = {
    'anthropic': 'Claude',
    'google': 'Gemini',
    'openai': 'GPT',
    'meta': 'Llama',           # bare meta provider
    'huggingface:meta-llama/*': 'Llama',  # HF-hosted Llama (pattern match)
    'ollama:qwen*': 'Qwen',    # local Qwen (pattern match)
    'mistral': 'Mistral',      # NEW v1.6: Judge E arbitration
    'mistralai/*': 'Mistral',  # NEW v1.6: HF-hosted Mistral pattern
}
```

The check enforces that no two judges (A, B, C, D, E) share a family. Judge D is Claude, Judge E is Mistral, Judges A/B/C are GPT/Gemini/Llama. Five distinct families total. The Phase 2 generator is also Claude family, which is intentional alignment with Judge D (not a violation): the calibration anchor and the corpus generator can share a family because the calibration role is anchor generation rather than independent verification.

If any production judge family matches another production judge family or matches Judge E's family or matches a non-Claude generator family, the command exits with code 5 and a diagnostic message.

The `--allow-same-family-judge` flag overrides (exits 0 with prominent warning), intended only for Stage 0 smoke testing, never for Stage 2 full-corpus runs.

### 6.3 Training data overlap caveat

All five judge families (Claude, GPT, Gemini, Llama, Mistral) may share training data on V&V 40, safety assurance, and credibility framework literature. This is a known limitation of all LLM-as-judge methodology. Five cross-family judges reduce single-family training-data dependence but do not eliminate it. Documented in Ch3 methodology section as a limitation with references to the LLM-as-judge literature (Zheng et al. 2023 MT-Bench, Dubois et al. 2024 AlpacaEval). The paper addendum (§20) addresses this via expert human reviewers.

### 6.7 Judge E: Mistral Large 2 as disagreement arbiter

Judge E is Mistral Large 2 operating as the disagreement arbiter for the reduce step of the protocol. Judge E processes only the inter-judge disagreement queue from Stage 3 triage, not the full corpus.

**Why Mistral Large 2.** The fifth judge must come from a family that does not appear elsewhere in the protocol. Anthropic Claude is Judge D, OpenAI is Judge A, Google is Judge B, Meta is Judge C. Three credible candidates remained: Mistral Large 2 (European frontier-tier), DeepSeek V3 (open-weights frontier), Cohere Command A (enterprise-positioned). Mistral Large 2 was selected as the primary because (1) European model origin is geopolitically neutral relative to US FDA submissions and avoids questions about Chinese-trained models in regulatory methodology, (2) the API is mature with reasoning-mode support comparable to other frontier judges, (3) Mistral has appeared in European AI safety and assurance research literature giving plausible relevant training corpus exposure, (4) competitive pricing within the contingency budget.

**Provider configuration.** Mistral Large 2 is accessed through the Mistral API directly using a thin adapter on the existing OpenAI-compat provider class:

```python
# uofa/adversarial/judge/providers/mistral.py

from openai import OpenAI
import os

class MistralProvider(AbstractJudgeProvider):
    """Mistral Large 2 via Mistral API."""

    def __init__(self):
        self.client = OpenAI(
            api_key=os.environ['MISTRAL_API_KEY'],
            base_url='https://api.mistral.ai/v1',
        )
        self.family = 'Mistral'
        self.supports_strict_schema = True  # Mistral API supports response_format json_schema
        self.model = 'mistral-large-2'
```

**Family independence rationale.** Judge D is Claude, Judge E is Mistral. The two LLM-anchor roles in the protocol (calibration source, disagreement arbiter) come from different families. This avoids the closed-loop circularity that would arise from using Claude in both roles, where the disagreement arbiter would resolve disagreements against ground truth the same model produced.

**Operational scope.** Judge E runs after Stage 2 full-corpus judgment completes and Stage 3 triage produces the disagreement queue. Judge E does not run on CONVERGENT cases. Expected disagreement queue at pairwise kappa 0.70-0.78 across A/B/C: 500-800 cases. Judge E runtime: ~6-12 hours wall clock at OpenAI-compat batch-equivalent throughput (Mistral does not have a batch API; synchronous concurrent requests with `--parallel N` instead).

**Prompt design.** Judge E receives a different prompt than the production judges (see §7.8). The prompt frames the task as arbitration of inter-judge disagreement: Judge E sees the package, the three production-judge verdicts with reasoning, and is asked to produce its own verdict plus an arbitration confidence score. Judge E does not see the calibration anchor (Judge D verdicts) for the disagreement cases, preserving independence from the calibration source.

**Confidence threshold.** Judge E produces a confidence score in [0.0, 1.0] for each arbitration. Cases with confidence ≥ 0.6 close at the Judge E layer; cases with confidence < 0.6 escalate to the author for final arbitration. The 0.6 threshold reuses the §10.1 confidence threshold for protocol consistency. Expected escalation rate: 10-15% of the disagreement queue, so 50-120 cases at 3-5 minutes per case = 2.5-10 hours of author final-arbitration time.

**Calibration sanity check.** Before Stage 4 arbitration, Judge E runs once over the 30-case calibration set as a sanity check. Per-class agreement with Judge D is reported informationally. Judge E is not required to match Judge D at any threshold; the agreement statistic is published as methodology transparency rather than as a gate.

| Position | Model | Provider | Family | Role |
|---|---|---|---|---|
| Judge E | mistral-large-2 with reasoning | Mistral | Mistral | Disagreement arbiter (reduce-step LLM) |

## 7. Judge prompt design

### 7.1 Prompt template v1.0.0 structure

The prompt has six sections assembled per-case. All three judges receive identical prompts.

1. **System framing** — role: "You are an expert in computational modeling and simulation credibility assurance, evaluating synthetic evidence packages generated for the Unit of Assurance (UofA) weakener catalog."
2. **Framework context** — V&V 40 overview, credibility factor definitions, UofA weakener catalog overview with all 14 patterns described
3. **Verdict class definitions with worked examples** — each of the 6 verdict classes defined with one canonical example drawn from the calibration set (few-shot anchor)
4. **Reasoning scaffold** — structured chain-of-thought template the judge must follow: (a) identify the source taxonomy, (b) identify the target rule, (c) inspect rule firings, (d) check whether package legitimately instantiates the defeater, (e) commit to verdict class
5. **Case content** — the full JSON-LD package, the Phase 2 outcome classification (COV-HIT / COV-MISS / COV-WRONG), which rules fired, which rule was expected
6. **Output instruction** — structured JSON output schema with strict field requirements

The framework context plus verdict class definitions plus reasoning scaffold (~12K tokens) is the static portion eligible for prompt caching. The case content (~3K tokens) varies per call.

### 7.2 Output schema

```json
{
  "case_id": "adv-2026-p2-002-gohar-data-drift-v03",
  "verdict": "CORRECT-DETECTION | REAL-GAP | GENERATOR-ARTIFACT | EXISTING-RULE-MISBEHAVIOR | OUT-OF-SCOPE | UNCERTAIN",
  "confidence": 0.87,
  "reasoning_steps": {
    "source_taxonomy_identified": "Gohar Evidence Validity / Data Drift",
    "target_rule_identified": "W-EV-01 (not yet in catalog)",
    "rule_firings_inspected": "No rules fired (COV-MISS)",
    "instantiation_check": "Package correctly instantiates Data Drift: validation dataset vintage 2018 predates model revision 2024 with no re-calibration",
    "verdict_commitment": "REAL-GAP"
  },
  "reasoning": "The package correctly instantiates Gohar Data Drift...",
  "section_6_7_candidate": "W-EV-01",
  "alternative_rule_analysis": "W-CON-03 shares some temporal semantics but operates on future-dated evidence only; not applicable here.",
  "prompt_template_version": "v1.0.0",
  "judge_model": "gpt-5.4",
  "judge_thinking_enabled": true,
  "judge_model_params": {
    "temperature": 0.0,
    "seed": 42
  },
  "generator_provenance": {
    "generator_model": "anthropic/claude-sonnet-4-6",
    "temperature": "N/A",
    "seed": "N/A"
  }
}
```

The `reasoning_steps` field is the structured chain-of-thought output. It's the single most effective lever for kappa improvement (§7.5).

### 7.3 Verdict class definitions in prompt

Each of the 6 verdict classes has a one-paragraph definition the judge sees, followed by one worked example from the calibration set. The 6-class structure handles COV-HIT (CORRECT-DETECTION), COV-MISS (REAL-GAP if package legitimate, else GENERATOR-ARTIFACT or OUT-OF-SCOPE), and COV-WRONG (EXISTING-RULE-MISBEHAVIOR if rule misfired, else GENERATOR-ARTIFACT). UNCERTAIN is the explicit escape hatch.

### 7.4 Prompt tuning methodology

Calibration is the tuning loop. Initial prompt → calibration run for each judge → per-judge accuracy check → prompt refinement if any judge is below 80% OR if pairwise calibration κ is below 0.70 → re-run for all three judges. Each prompt version is committed to `packs/core/judge_prompts/vX.Y.Z.md` with a changelog. Per Principle 6, all judges use the same final prompt version.

Up to 3 tuning iterations. If thresholds not met after 3 iterations, escalate per §8.3.

### 7.5 Kappa-improvement methodology (new in v1.4)

Five prompt design choices lift inter-judge agreement, ranked by expected impact:

| Lever | Implementation | Expected κ lift |
|---|---|---|
| Few-shot examples per verdict class | One canonical example per class drawn from calibration set, embedded in prompt §3 | +0.10-0.15 |
| Structured chain-of-thought scaffold | Required `reasoning_steps` field with 5 named sub-fields, judge must populate before committing verdict | +0.05-0.10 |
| Calibration-driven prompt refinement | After calibration, identify the lowest-accuracy verdict class per judge; revise that class's definition and worked example; re-run calibration | +0.05-0.10 |
| Temperature 0.0 + fixed seed | Both vendors support; reduces stochastic disagreement | +0.02-0.05 |
| SOTA models with thinking enabled | GPT-5.4 + Gemini 3.1 Pro both with extended reasoning | +0.05-0.08 (already baked into model selection) |

Combined expected lift over the v1.3 baseline (~0.6): ~0.70-0.78 pairwise κ achievable. Realistic v1.4 target: ≥0.70 pairwise κ. Target of 0.85 is unrealistic for defeater triage and should not be pursued through prompt engineering tricks that risk biasing the judges.

### 7.6 Anti-patterns prohibited in prompt design

To preserve methodology validity, the prompt must NOT:

* Bias toward a default verdict (e.g., "when uncertain, default to GENERATOR-ARTIFACT")
* Include the §6.7 expected mapping for the case being judged
* Show one judge the verdict from another judge
* Remove UNCERTAIN as a verdict class
* Reduce the verdict class count for ease of judging

Any of these would inflate kappa while destroying its meaning. Honest agreement at κ = 0.72 is more defensible than gamed agreement at κ = 0.92.

### 7.7 Output format and structured output mode (new in v1.5)

The judge output format is JSON, validated against `specs/judge_output_schema.json`. Per-judge output mode depends on what the API supports:

| Judge | Output mode | Schema enforcement | Failure mode handling |
|---|---|---|---|
| Judge A (OpenAI gpt-5.4) | `response_format={'type': 'json_schema', 'json_schema': SCHEMA, 'strict': True}` | API-enforced strict schema | Cannot return malformed output; parse always succeeds |
| Judge B (Gemini 3.1 Pro) | `response_mime_type='application/json'`, `response_schema=SCHEMA` | API-enforced schema (Gemini equivalent of strict mode) | Cannot return malformed output; parse always succeeds |
| Judge C (Llama 3.3 70B via HF Endpoints) | JSON-mode in prompt instruction; HF TGI does not support strict schema | Prompt-level instruction only; no API enforcement | Tolerant parser fallback in `judge.py` similar to extract eval pattern; failed cases logged to `failures/hf-llama/` |

**Output format principle.** Use the strongest reliability mode each context supports.

* JSON with API-enforced strict schema: OpenAI and Gemini judges. This is the strongest reliability mode and eliminates malformed-output failure modes.
* JSON-mode without strict schema enforcement, plus tolerant parser fallback: Llama via HF Endpoints (TGI does not support schema enforcement). Also any future contexts where a frontier-tier model is accessed through an API without schema enforcement.
* Key-value (kv) format with line-based deterministic parsing: bundled small local models (e.g., `--explain` flag with bundled qwen3.5:4b). Per the extract eval, kv eliminates the brace-drop failure mode that affects ~25-33% of long structured JSON outputs from 4B local models.
* YAML is **not used** as a structured output format anywhere in the UofA pipeline. No major LLM API vendor supports YAML schema enforcement. The kv format provides equivalent benefits for small local models without YAML's indentation fragility.

The extract eval kv pivot logic does not generalize to frontier APIs because frontier APIs solve the same problem at a different layer (API-level schema enforcement). The principle is per-context selection of the strongest available reliability mode, not universal kv adoption.

**Schema definition.** `specs/judge_output_schema.json` is the single source of truth for the judge output structure. It is consumed by:

1. The OpenAI provider via `response_format.json_schema`
2. The Gemini provider via `response_schema`
3. The judge parser via `jsonschema.validate()` (post-parse validation, especially for the HF Llama case)
4. The unit tests via fixture validation

Schema sketch (full schema in `specs/judge_output_schema.json`):

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["case_id", "verdict", "confidence", "reasoning_steps", "judge_model"],
  "properties": {
    "case_id": {"type": "string", "pattern": "^adv-2026-p2-\\d+-.+-v\\d+$|^cal-\\d+-.+$"},
    "verdict": {"type": "string", "enum": ["CORRECT-DETECTION", "REAL-GAP", "GENERATOR-ARTIFACT", "EXISTING-RULE-MISBEHAVIOR", "OUT-OF-SCOPE", "UNCERTAIN"]},
    "confidence": {"type": "number", "minimum": 0.0, "maximum": 1.0},
    "reasoning_steps": {
      "type": "object",
      "required": ["source_taxonomy_identified", "target_rule_identified", "rule_firings_inspected", "instantiation_check", "verdict_commitment"],
      "properties": {
        "source_taxonomy_identified": {"type": "string", "minLength": 10},
        "target_rule_identified": {"type": "string", "minLength": 5},
        "rule_firings_inspected": {"type": "string", "minLength": 10},
        "instantiation_check": {"type": "string", "minLength": 20},
        "verdict_commitment": {"type": "string", "enum": ["CORRECT-DETECTION", "REAL-GAP", "GENERATOR-ARTIFACT", "EXISTING-RULE-MISBEHAVIOR", "OUT-OF-SCOPE", "UNCERTAIN"]}
      }
    },
    "reasoning": {"type": "string", "minLength": 50},
    "section_6_7_candidate": {"type": ["string", "null"]},
    "alternative_rule_analysis": {"type": ["string", "null"]},
    "prompt_template_version": {"type": "string"},
    "judge_model": {"type": "string"},
    "judge_thinking_enabled": {"type": "boolean"},
    "judge_model_params": {"type": "object"},
    "generator_provenance": {"type": "object"}
  }
}
```

The strict schema constraint means a malformed output cannot be returned from OpenAI or Gemini. For Llama via HF Endpoints, the tolerant parser handles the rare malformed case by retrying once with a more explicit reformat instruction, then logging to `failures/hf-llama/` if still malformed.

### 7.8 Judge E arbitration prompt (new in v1.6)

Judge E (Mistral Large 2) receives a different prompt from the production judges A/B/C. The arbitration prompt frames the task explicitly as resolving inter-judge disagreement rather than producing an independent verdict.

**Prompt structure (six sections):**

1. **System framing.** "You are an expert in computational modeling and simulation credibility assurance, asked to arbitrate disagreements between three independent LLM judges who have evaluated a synthetic evidence package."
2. **Framework context.** Same V&V 40 + UofA catalog overview as the production-judge prompt §7.1.
3. **Verdict class definitions.** Same 6 verdict classes with one canonical example per class drawn from the calibration set. Note: Judge E sees the calibration set few-shot examples, but does not see Judge D's verdict on the specific case being arbitrated.
4. **Inter-judge disagreement summary.** The three production-judge verdicts (Judge A, Judge B, Judge C), confidences, and `reasoning_steps` presented side-by-side with the disagreement type explicitly named (e.g., "Judges A and B agree REAL-GAP; Judge C says EXISTING-RULE-MISBEHAVIOR").
5. **Case content.** The full JSON-LD package, the Phase 2 outcome classification, which rules fired, which rule was expected. Same as the production-judge prompt §7.1.
6. **Output instruction.** Structured JSON schema requiring a verdict, confidence in [0.0, 1.0], reasoning that explicitly addresses the disagreement (which production-judge reasoning is most sound and why), and an arbitration_basis field naming whether the verdict came from package content alone, from production-judge reasoning evaluation, or from explicit disagreement with all three production judges.

**Output schema (extends §7.7):**

```json
{
  "case_id": "adv-2026-p2-002-...",
  "verdict": "REAL-GAP | CORRECT-DETECTION | ... | UNCERTAIN",
  "confidence": 0.72,
  "reasoning_steps": { ... same as §7.7 ... },
  "arbitration_basis": "package_content | production_judge_evaluation | independent_disagreement",
  "production_judge_evaluation": {
    "judge_a_reasoning_assessment": "sound | weak | irrelevant",
    "judge_b_reasoning_assessment": "sound | weak | irrelevant",
    "judge_c_reasoning_assessment": "sound | weak | irrelevant"
  },
  "judge_role": "arbiter",
  "judge_model": "mistral-large-2",
  ...
}
```

**Prompt anti-patterns (extends §7.6):**

The arbitration prompt must NOT:

* Show Judge D's calibration verdict for the specific case being arbitrated (would collapse Judge E to Judge D agreement).
* Bias toward majority of production judges (e.g., "go with the majority unless clearly wrong"). Judge E should arbitrate on substantive grounds.
* Use confidence as a tie-breaker against Judge E's own judgment ("if you can't decide, default to the high-confidence production judge"). Judge E should produce its own confidence based on its own reasoning, not anchor against production-judge confidence.

**Prompt versioning.** The Judge E prompt has a separate version stream from the production-judge prompt. `packs/core/judge_prompts/arbitration_v1.0.0.md` is the initial Judge E prompt. Tuning iterations are independent of A/B/C prompt tuning.

## 8. Calibration methodology (Stage 1)

### 8.0 Calibration anchor generation (Judge D, Stage 0.5)

Stage 0.5 is the calibration anchor generation step. It runs once before Stage 1 calibration and produces the ground-truth verdicts the production judges will be measured against.

**Process:**

1. Author confirms the 30-case calibration set selection from the Phase 2 corpus (stratified by verdict class per §8.1; produced by the calibration set scaffolder).
2. Judge D (Anthropic Claude Sonnet 4.6 minimum, with extended thinking enabled) processes each of the 30 cases using the standard production-judge prompt §7.1.
3. Judge D output is written to `out/adversarial/phase3/calibration/judge_d_anchor.jsonl`. Each line is a complete §7.7 schema judgment record with `judge_model: "claude-sonnet-4-6"` and `judge_role: "calibration_anchor"`.
4. Author reviews each Judge D verdict against the package content. Cases where the author overrides Judge D are recorded in `out/adversarial/phase3/calibration/judge_d_author_overrides.jsonl` with `original_verdict`, `override_verdict`, `override_rationale` fields.
5. The override-applied calibration set is written to `specs/calibration/calibration_set_v1.jsonl` in the §22 schema. This is the calibration anchor that Judges A/B/C calibrate against in Stage 1.

**Author override authority.** The author may override Judge D verdicts on any case. Override frequency and rationale are reported in the praxis methodology section as a transparency signal. The expected override rate is low (Judge D is competent on the methodology task) but non-zero overrides demonstrate active author engagement with the calibration anchor.

**Validity property.** The Judge D anchor is the calibration source for Judges A/B/C. The validity claim is "LLM-generated calibration anchor with author sanity-check review and override authority." This claim is precise and bounded. The defense methodology section names the claim explicitly without inflating it.

**Cost.** 30 cases × ~$0.015 per call ≈ $0.50. Negligible.

### 8.1 Calibration set construction

30 cases with stratified sampling balanced across the 6 verdict classes. Verdicts are generated by Judge D in Stage 0.5; the author may override per §8.0:

| Verdict class | Count | Source |
|---|---|---|
| CORRECT-DETECTION | 5 | Stratified-sampled from Phase 2 COV-HIT cases where rule firing matches expected target cleanly |
| REAL-GAP | 5 | Stratified-sampled from Phase 2 gap_probe + COV-WRONG cases mapping to §6.7 Tier 1 candidates (≥4 of 6 candidates covered) |
| GENERATOR-ARTIFACT | 5 | Stratified-sampled from Phase 2 GEN-INVALID cases (SHACL-failed packages) |
| EXISTING-RULE-MISBEHAVIOR | 5 | Stratified-sampled from Phase 2 negative_control + COV-CLEAN-WRONG cases (false positives on clean COUs) |
| OUT-OF-SCOPE | 5 | Author-constructed packages instantiating out-of-scope defeaters (subjective model-form adequacy, human factors, organizational, regulatory jurisdiction, clinical judgment) |
| UNCERTAIN | 5 | Stratified-sampled from Phase 2 confirm_existing + COV-WRONG cases where the target rule did not fire and the resolution genuinely resists determination |

The OUT-OF-SCOPE class is the only one requiring author-constructed packages because Phase 2 does not generate out-of-scope cases by design. The other five classes draw from the Phase 2 corpus.

### 8.2 Calibration set storage

```
specs/calibration/calibration_set_v1.jsonl
```

Each line follows the JSON schema in Appendix B.

### 8.3 Calibration accuracy targets

Per-judge accuracy = (count of judge verdicts matching ground truth) / 30, computed independently for each judge.

Pairwise calibration κ = Cohen's κ between each pair of judges on the 30-case set, before exposure to the full corpus.

* Per-judge target: ≥ 80% accuracy (24/30 correct) for each of the three judges
* Pairwise calibration κ target: ≥ 0.70 for all three pairs (GPT-Gemini, GPT-Llama, Gemini-Llama)
* Per-class accuracy target: ≥ 50% per verdict class per judge (soft within hard)

If thresholds not met on default prompt: tune prompt, version bump, re-run for all three judges. Up to 3 tuning iterations.

If after 3 iterations one judge remains below 80% but the other two meet it: proceed to Stage 2 with that judge flagged in agreement statistics. Document the failure mode in Ch3.

If after 3 iterations two or more judges remain below 80%: escalate. Options: (a) substitute a different SOTA flagship for the failing judge (e.g., GPT-5.4-pro variant), (b) accept lower per-judge accuracy with documented rationale, (c) expand calibration set to diagnose failure modes.

### 8.4 Per-class accuracy disclosure

In addition to overall per-judge accuracy, calibration output reports per-class accuracy for each judge. The per-class table appears in Ch3 methodology and is a soft gate (target ≥ 50% per class per judge). It also feeds the calibration-driven prompt refinement loop in §7.5.

## 9. Full-corpus judgment (Stage 2)

### 9.1 CLI surface

```bash
uofa adversarial judge \
  --in out/adversarial/phase2/judge_ready_bundle.tgz \
  --out out/adversarial/phase3/judgments/ \
  --judges openai,gemini,hf-llama \
  --model-openai gpt-5.4 \
  --model-openai-thinking enabled \
  --model-gemini gemini-3.1-pro \
  --model-gemini-thinking enabled \
  --model-hf-llama meta-llama/Llama-3.3-70B-Instruct \
  --hf-endpoint-url https://your-endpoint.endpoints.huggingface.cloud \
  --prompt-version v1.0.0 \
  --enable-prompt-caching \
  --enable-batch-api \
  --calibration-check \
  --parallel 8
```

`--judges` accepts a comma-separated list. Three required for v1.4 default. Cross-family circularity check (§6.2) applies before any judgment runs.

`--enable-prompt-caching` activates vendor-specific cache keys for the static prompt prefix (~12K tokens of framework context plus verdict class definitions plus reasoning scaffold). Both OpenAI and Gemini support cache hits at ~90% discount on cached input tokens.

`--enable-batch-api` submits the full-corpus judgments as batch jobs (24-hour SLA) for 50% discount on both OpenAI and Gemini. The HF Endpoints judge uses normal request flow (no batch concept on dedicated infrastructure).

### 9.2 Semantics

* Reads the Phase 2 judge-ready bundle (all packages, all coverage classes) via the §2.1 bundle reader
* For each package, loads the JSON-LD plus rule-engine output
* Assembles prompt per §7.1 (identical prompt for all judges, with cache-friendly static prefix)
* Applies structured output mode per §7.7: OpenAI strict schema, Gemini schema, Llama JSON-mode-plus-tolerant-parser
* For OpenAI and Gemini: submits batched requests; polls for completion within 24 hours
* For HF Endpoints (Llama): runs synchronously with `--parallel N` concurrent requests against the dedicated endpoint
* Writes per-case-per-judge judgment to `judgments/{case_id}__{judge}.json` and appends to `judgments_{judge}.jsonl`
* Aggregates per-judge statistics: verdict class distribution, confidence distribution, median processing time
* `--calibration-check` re-runs the calibration set across all three judges as a sanity check and warns if accuracy has drifted

**Retry strategy (new in v1.5).** All judge API calls use exponential backoff with jitter via `uofa/adversarial/judge/retry.py`. Configuration:

* Max retries: 3 per call
* Initial delay: 1 second
* Backoff factor: 2.0 (1s → 2s → 4s)
* Jitter: ±25% of computed delay
* Retry on: HTTP 5xx, timeout, rate limit (HTTP 429 with Retry-After header honored)
* Do NOT retry on: HTTP 4xx (except 429), schema validation failures, authentication errors
* Failed cases after retry exhaustion: log full request/response to `failures/{judge}/{case_id}.json`, continue to next case

Schema validation failures are not retried because the failure is in the model's reasoning, not in transport. They are logged and surfaced for prompt tuning evaluation.

**Concurrency model (new in v1.5).** The `--parallel N` flag applies only to the HF Endpoints (Llama) judge.

* OpenAI and Gemini batch APIs are vendor-managed; concurrency is controlled by the vendor's batch infrastructure. The `--parallel` flag is ignored for these.
* HF Endpoints synchronous flow uses `asyncio` with `aiohttp` for concurrent requests against the dedicated H200 endpoint. `--parallel 8` means 8 in-flight requests at any time. Default 8 is calibrated to keep the H200 utilized without overwhelming the endpoint.
* CLI surface: `--parallel` only applies when `hf-llama` is in the `--judges` list. Validation: error if `--parallel` is set and `hf-llama` is not in `--judges`.

## 10. Inter-judge triage and Judge E arbitration (Stage 3)

### 10.1 Stage 3a: Production-judge triage buckets

The Stage 3a triage module partitions the 4,221 cases into three bins based on majority-of-3 inter-judge agreement among Judges A, B, C:

| Bucket | Criteria | Expected size at pairwise κ ≈ 0.72 | Next step |
|---|---|---|---|
| CONVERGENT | ≥ 2 of 3 production judges agree on verdict, all agreeing judges with confidence ≥ 0.6 | ~3,200-3,400 cases (~80-85%) | Close at production-judge layer; CONVERGENT verdict is the final verdict |
| DISAGREEMENT | All 3 disagree, OR 2 disagree + 1 UNCERTAIN, OR ≥ 2 agree but with confidence < 0.6, OR ≥ 2 return UNCERTAIN | ~500-800 cases (~12-19%) | Route to Judge E arbitration (Stage 3b) |

DISAGREEMENT cases form the Judge E arbitration queue. CONVERGENT cases close at the production-judge layer with the majority verdict as final.

### 10.2 Stage 3b: Judge E arbitration

Judge E (Mistral Large 2) processes the DISAGREEMENT queue per the §6.7 protocol and §7.8 prompt design. Output per case:

* `verdict`: one of the 6 verdict classes
* `confidence`: float in [0.0, 1.0]
* `reasoning_steps`, `reasoning`, `arbitration_basis`, `production_judge_evaluation`: per §7.8 schema

Stage 3b output is partitioned into two bins by Judge E confidence:

| Bucket | Criteria | Expected size | Next step |
|---|---|---|---|
| ARBITRATED | Judge E confidence ≥ 0.6 | ~85-90% of DISAGREEMENT queue (~430-720 cases) | Close at Judge E layer; arbitrated verdict is the final verdict |
| ESCALATED | Judge E confidence < 0.6 | ~10-15% of DISAGREEMENT queue (~50-120 cases) | Route to author final-arbitration (Stage 4) |

The 0.6 confidence threshold is the same threshold used in Stage 3a CONVERGENT bucketing for protocol consistency.

### 10.3 Final escalation queue assembly

The author final-arbitration queue is the ESCALATED bin from Stage 3b plus any cases the author elects to spot-check. Each queue entry includes:

* Case ID
* Source taxonomy attribution
* Excerpt of the synthetic package
* Phase 2 outcome summary
* All three production-judge verdicts, confidences, reasoning side-by-side
* Judge E arbitration verdict, confidence, reasoning, arbitration_basis, production_judge_evaluation
* Computed disagreement type and Judge E confidence

Format: a single CSV `out/adversarial/phase3/escalation_queue.csv` plus a directory `escalation_packets/` with one Markdown packet per case (per §23 template extended for Judge E inclusion).

### 10.4 Author time budget

Expected residual escalation queue: 50-120 cases. At ~3-5 minutes per case for author final-arbitration: 2.5-10 hours of author time. The author may also spot-check ARBITRATED cases at any time; recommended spot-check sample: 30-50 randomly-drawn ARBITRATED cases at ~2 minutes each (~1-2 hours). Total expected author wall time on Stage 4: 4-12 hours, well within the four-week execution window.

The §11.4 stratified-sample backstop from v1.4/v1.5 becomes mostly obsolete because the residual queue is structurally bounded by Judge E confidence thresholds rather than by full-queue annotation requirements. Section retained as a fallback if the residual queue exceeds 30 hours despite the Judge E layer.

## 11. Author final-arbitration protocol (Stage 4)

### 11.1 Final-arbitration input

The author works through `escalation_queue.csv` row by row, reading each Markdown packet. The packet contains the package, all production-judge verdicts and reasoning, the Judge E arbitration verdict and reasoning, and the Judge E confidence score. For each case, the author records:

* `final_verdict` — one of the six verdict classes
* `final_arbitration_rationale` — minimum 50 words referencing the package content, the production-judge disagreement, and the Judge E arbitration reasoning
* `agrees_with_judge_a` / `_b` / `_c` / `_e` — booleans, derived for stats
* `would_add_to_catalog` — yes/no/depends, informs Stage 5 formalization (relevant for REAL-GAP verdicts)
* `notes` — free-form, optional

Output: `out/adversarial/phase3/adjudications.jsonl`.

### 11.2 Final-arbitration conventions and override authority

The author may resolve any escalated case to any of the six verdict classes, including UNCERTAIN if the case genuinely resists determination per spec §11.2 v1.5 carryover. Final UNCERTAIN verdicts are excluded from catalog-extension decisions but preserved in the agreement statistics.

The author retains override authority on every case in the protocol, not just on escalated cases. Spot-check overrides on CONVERGENT or ARBITRATED cases are permitted and recorded in `out/adversarial/phase3/spot_check_overrides.jsonl` with `original_verdict` (CONVERGENT or ARBITRATED), `override_verdict`, `override_rationale` fields. Spot-check overrides are reported in the praxis methodology section as a transparency signal of author engagement with the auto-arbitrated cases.

### 11.3 Self-blinding sanity check

To partially mitigate author bias toward §6.7 expectations, the author records each final-arbitration verdict before reading the §6.7 Tier 1 expectation tag for that case. The expectation tag is then revealed and a `post_hoc_alignment` field is recorded indicating whether the verdict matched, contradicted, or was independent of the §6.7 expectation. This produces an honest signal of how much §6.7 expectation drives author final-arbitration versus how much the package content and judge reasoning drive it.

### 11.4 Stratified-sample backstop (legacy from v1.4/v1.5; mostly obsolete in v1.6)

In v1.4/v1.5 the stratified-sample backstop was the primary mechanism for keeping author adjudication tractable when the DIVERGENT + UNCERTAIN queue exceeded 30 hours. In v1.6 the Judge E arbitration layer reduces the residual escalation queue to 50-120 cases by construction, making stratified sampling unnecessary in normal execution.

The backstop is retained as a fallback for two scenarios: (1) Judge E unavailable mid-execution and must be substituted with a different fifth-family model that produces low-confidence on most cases, inflating the escalation queue; (2) the production-judge pairwise kappa lands well below 0.70 and the disagreement queue exceeds 1500 cases such that even the 10-15% escalation rate produces an unmanageable residual.

If invoked, the stratified sample design is unchanged from v1.5 §11.4: 100% of §6.7 Tier 1 candidate cases, 30 cases per top-5 source taxonomy, 100% of all-three-disagree cases, plus random samples of remaining categories. Total: ~150-200 cases, ~6-8 hours of author time.

Decision (full escalation queue versus stratified sample) is logged in `out/adversarial/phase3/adjudication_method.txt` with rationale.

## 18. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Any of three judges stuck below 80% calibration accuracy | Medium | Up to 3 prompt tuning iterations using §7.5 levers. If one judge fails persistently, substitute alternative SOTA model in same family (e.g., gpt-5.4-pro). If two or more fail, escalate per §8.3. |
| Pairwise calibration κ below 0.70 even with §7.5 prompt engineering | Medium | Document honestly. Proceed to Stage 2 with the lower-agreement judge pair flagged. The DIVERGENT bin grows, author adjudication time grows accordingly. Stratified-sample backstop activates if queue exceeds budget. |
| All three judges share LLM blind spot (high agreement, all wrong) | Medium | Three-judge ensemble cannot detect this. Per-judge calibration accuracy on author-annotated set is the partial mitigation. Honest disclosure in Ch3 limitations + paper addendum motivation. Three families reduces single-vendor blind-spot risk vs two-judge but does not eliminate shared-pretraining blind spots. |
| Adjudication queue exceeds 30 author hours | Medium-High | §11.4 stratified-sample backstop. Decision documented in adjudication_method.txt. Praxis claim still defensible. |
| HF Endpoints cold start consumes excessive billed time | Low-Medium | Single spinup per session (calibration + full corpus = 2 spinups total). Avoid scale-to-zero between sessions during active Phase 3. Documented in §6.5. |

| OpenAI batch API submission errors or partial failures | Low-Medium | Retry logic with exponential backoff; failures isolated to per-case fallback to synchronous API at standard pricing. Cost impact minimal since batch failure rate typically < 5%. |
| Gemini batch API similar failure pattern | Low-Medium | Same mitigation as OpenAI. |

## 19. Open questions

1. **Calibration set visibility.** Should `specs/calibration/calibration_set_v1.jsonl` be committed to the public repo or kept private? Default: committed publicly with `specs/calibration/annotation_rationale.md` explaining each ground-truth annotation. Invite community critique as future work.

Document any substitution in run manifest. Cross-family substitution requires re-running Stage 1 calibration to revalidate κ thresholds.

5. **Catalog version numbering.** v0.4.0-nafems frozen. v0.4.1 includes Phase 2 schema additions. v0.5 includes Phase 3 rule additions. Standard semver continues.

6. **Stratified vs full-queue adjudication decision criteria.** Default: full-queue if estimated author time ≤ 30 hrs; stratified otherwise. The threshold is documented but the author has discretion to invoke stratified earlier if other factors (illness, travel) compress capacity.

7. **HF Endpoint region selection.** Default: AWS us-east-1 for lowest latency from US. Author may choose EU region if data residency becomes a concern (synthetic packages are not sensitive, so this is not anticipated).

8. **Post-Phase 3 roadmap.** Reframe completion and delivery to Turman (early July); praxis Ch3 + Ch5 drafting (July-August); paper addendum scoping for post-defense human reviewer extension. Phase 3 artifacts feed directly into both the praxis and the future paper.
